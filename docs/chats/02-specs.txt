⏺ I've written the spec to docs/specs/bulk-payments.md. It follows the same
  structure as products.md: numbered FR, LIM and CON items that reference each
  other, an error table and a security section. Nothing is committed.

  Your choices, as written:
  - Schema: the brief's columns and types exactly (CON-1). The brief's seed
    INSERT has to run unmodified, so constraints and indexes can be added but
    columns can't.
  - Locking: the payer and payee rows are locked in ascending id order before
    the funds check (FR-7).
  - Status codes: 400 for a malformed request, 404 for an unknown payer, 422 for
    business denials, which include an unknown payee, insufficient funds and a
    payee balance that would overflow.
  - Idempotency: an optional Idempotency-Key header, stored in a new
    idempotency_keys table in the same transaction as the payments (FR-9).
  - Limits: at most 1,000 payments per request, a required description of up to
    255 characters, strict amount strings, and no paying yourself (400).

  Defaults I chose without asking. Change any you disagree with:
  - Self-payment is a 400, not a 422. Your second answer filed it under 400
    limits, and that overrides the round-1 split.
  - Lock waits time out after 5 seconds with a 503 busy, which is safe to retry
    (LIM-9).
  - Denials aren't stored against the idempotency key, so a retry after a 422 is
    evaluated again. A replayed success carries an Idempotent-Replayed: true
    header.
  - The insufficient_funds response never shows the payer's balance, because the
    service has no authentication. It only reports the required total.
  - A 400 lists every bad entry by its index, not just the first one.
  - Unknown fields in the request are ignored.
  - Errors are checked in a fixed order: 400, then 404, then 409 or replay,
    then 422.

  ★ Insight ─────────────────────────────────────
  - Rails won't match CON-1 by default. Rails 8 creates bigint primary keys, and
    t.references creates bigint foreign keys. To keep the brief's literal
    INTEGER types, the migrations need id: :integer and type: :integer on the
    references.
  - The brief's sample request is the acceptance test. It pays one payee twice,
    so it covers both "don't merge entries" and "credit the sum per payee" in a
    single request. Pinning it as CON-5 gives the implementation a check against
    the brief's own numbers.

❯ which requirement is responsible for atomic transaction?                      

⏺ FR-6 (Funds Check and Settlement) owns it. Two of its bullets cover it:

  - The system "SHALL, in a single database transaction, insert the bulk payment
    and every payment, debit the payer by exactly the total, and credit each
    payee by exactly the sum of its entries."
  - "Settlement SHALL be all-or-nothing. A denied or failed request leaves no
    bulk payment, no payment rows, and no balance change."

  Other requirements touch the same transaction from other angles:

  ┌───────────────────────────────┬─────────────────────────────────────────┐
  │          Requirement          │              What it adds               │
  ├───────────────────────────────┼─────────────────────────────────────────┤
  │ NFR-2 (Data Integrity), first │ Isolation: no reader on any instance    │
  │  bullet                       │ sees half of a request.                 │
  ├───────────────────────────────┼─────────────────────────────────────────┤
  │                               │ Row locks are taken inside the          │
  │ NFR-1 (Concurrency)           │ transaction, and a lock timeout (503)   │
  │                               │ leaves no partial state.                │
  ├───────────────────────────────┼─────────────────────────────────────────┤
  │                               │ The key is written in the same          │
  │ FR-8 (Idempotent Retries)     │ transaction, so a key exists only if    │
  │                               │ its payments committed.                 │
  ├───────────────────────────────┼─────────────────────────────────────────┤
  │ FR-2, "A denied or failed     │ Repeats FR-6's all-or-nothing rule for  │
  │ request SHALL leave no bulk   │ the bulk payment row.                   │
  │ payment"                      │                                         │
  └───────────────────────────────┴─────────────────────────────────────────┘

  The FR-2 bullet is redundant, since FR-6 already says "no bulk payment". I can
  delete it, or change it to point to FR-6, so the rule lives in one place.

  ★ Insight ─────────────────────────────────────
