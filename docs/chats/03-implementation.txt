     Plan: Bulk Payments (POST /bulk_payments)

     Context

     docs/specs/bulk-payments.md specifies a bulk payment endpoint: one payer
     firm pays many payee firms in a single all-or-nothing request, with a
     row-locked funds check, mandatory idempotency keys, and deadlock-free
     behavior across multiple instances over one PostgreSQL DB (READ COMMITTED).
     The repo is a fresh Rails 8.1 API app whose only domain code is an
     unrelated Payment scaffold (currency/status columns) that must be replaced.

     User decisions: remove only the Payment feature scaffold (Rails framework
     defaults stay); immutability app-level only (keep schema.rb); tests stay in
     the git commit hook (no GH Actions change); brief schema confirmed from
     screenshot — firms(id INTEGER, name TEXT, balance_cents INTEGER, uuid 
     TEXT), payments(id, payer_firm_id, payee_firm_id, amount_cents INTEGER, 
     description TEXT), no timestamps.

     Delete: app/models/payment.rb (rewritten),
     app/controllers/payments_controller.rb, resources :payments route,
     spec/factories/payments.rb, spec/models/payment_spec.rb,
     spec/requests/payments_spec.rb (keep the /up health check example → move to
     spec/requests/health_spec.rb),

     migrated over). Local dev/test DBs get bin/rails db:drop db:create

     2. Schema (new migrations, schema.rb regenerated)

     firms and payments keep exactly the brief's columns and types (screenshot).
     No t.timestamps on either table, no renamed or retyped columns. The only
     column added is payments.bulk_payment_id, which the spec allows. Ids are
     create_table … id: :integer (serial INTEGER). FKs use type: :integer.
     Strings are t.text. Everything else on these two tables is a constraint or
     an index.

     - CON-1: list NOT NULL explicitly among the additions allowed on brief
       columns (it currently names only indexes, FKs, and checks).
     - FR-4: add a 400 for a description that contains a NUL or isn't valid

     - NFR-1: say the 5s bound covers acquiring the whole lock set, not each row

     3. Models (app/models/)

     - Firm — has_many none needed; plain.
     - BulkPayment — belongs_to :payer_firm, has_many :payments, -> { order(:id)
       }; readonly? when persisted.
     - Payment — belongs_to :bulk_payment, :payer_firm, :payee_firm; readonly?

     No AR validations duplicating the request validator — the service validates
     the request; DB enforces invariants.

     4. Services (app/services/bulk_payments/)

     - Amount — parse(str) -> Integer cents | nil via
       /\A(\d+)(?:\.(\d{1,2}))?\z/ (Ruby \d is ASCII-only). Computes
       dollars.to_i * 100 + frac.ljust(2, "0").to_i. String#to_i is always base
       10, so "010" is 10, not octal 8. Never Kernel#Integer without a base.
       Strings over 20 chars are rejected before parsing. No Float or BigDecimal
       anywhere. format(cents) -> "%d.%02d". MAX_CENTS = 2_147_483_647.
     - RequestParser — input: raw body + Idempotency-Key header. JSON.parse the
       raw body (controller disables wrap_parameters, never touches params).
       Validates every FR-4 rule and collects all errors. Descriptions that
       contain \u0000 or fail valid_encoding? (lone surrogates) are rejected.
       UUIDs are lowercased before lookup and fingerprinting, so an uppercase
       uuid neither 404s nor produces a different fingerprint. Output: Request
       value object (idempotency_key, payer_uuid, entries[{payee_uuid, 
       amount_cents, description}], total_cents) or a 400 error with details: { 
       errors: [{field:, message:}], payments: [{index:, errors: {amount: [...],
       ...}}] }.
     - Fingerprint — SHA256.hexdigest(JSON.generate([payer_uuid, entries.map { 
       [payee_uuid, amount_cents, description] }])).
     - Create — orchestrator returning Result(status, body, replayed):
       a. (pre-txn) resolve payer by uuid → 404 payer_not_found.
       b. (pre-txn) idempotency fast path: lookup (payer_id, key) → replay (201
          + Idempotent-Replayed) or 409. Safe: bulk payments are immutable and
          never deleted.
       c. (pre-txn) resolve distinct payee uuids in one query → 422
          payee_not_found with all unknown uuids. Safe: firms are never deleted
          / uuids never change.
       d. Transaction:
          - SET LOCAL statement_timeout (the 5s bound), then SELECT id, 
            balance_cents FROM firms WHERE id IN (...) ORDER BY id FOR UPDATE,
            then SET LOCAL statement_timeout = DEFAULT. One statement locks rows
            in ascending id order (LockRows sits above Sort), and the timeout
            caps the total wait for the whole set.
          - Re-check idempotency under the payer lock.
          - Funds check → 422 insufficient_funds (details.required_total, never
            the balance).
          - Per-payee aggregated limit check → 422 payee_balance_limit_exceeded
            (lists payee uuids).
          - Insert the bulk payment.
          - Allocate payment ids ascending with SELECT 
            nextval(pg_get_serial_sequence('payments','id')) FROM 
            generate_series(1, n) sorted, then insert_all in request order.
          - One UPDATE debits the payer; one UPDATE … FROM (VALUES …) credits
            the payees.
       e. ActiveRecord::QueryCanceled raised by the lock statement only → 503
          busy. RecordNotUnique on the idempotency index → re-run step 2 (replay
          or 409).
     - Serializer — builds the 201 body from a persisted BulkPayment + payments
       (ordered by id). Used for both original and replay so they match by
       construction.
     - Error — (status, code, message, details) → { error: { code, message, 
       details } }.

     Lock-wait bound: Rails.configuration.x.bulk_payments.lock_wait_ms (default
     5000), applied as SET LOCAL statement_timeout around the lock statement
     only.

     5. Controller / route

     post "bulk_payments" => "bulk_payments#create".
     BulkPaymentsController#create: wrap_parameters false; call parser → Create;
     render result JSON, set Idempotent-Replayed: true on replay. Unexpected
     errors → 500 JSON internal_error (transaction already rolled back).

     - spec/requests/bulk_payments_spec.rb (transactional): AC-1 verbatim

       balance sum invariant); one describe per FR (FR-3 extra fields ignored;
       FR-4 every bullet incl. multi-index reporting; FR-5 404/422 lists all
       unknown; FR-6 exact-balance boundary accepted, 1 cent short denied with
       no state change, payee limit incl. same-payee aggregation; FR-7 formats;

       drained, normalization variants ("300"/"300.00", key order, whitespace,
       uppercase uuid) replay, different body → 409, retry after 422
       re-evaluated, keys scoped per payer); error precedence (400>404>409>422).
     - Money/float matrix (request-level +
       spec/services/bulk_payments/amount_spec.rb): "0.1"+"0.2" → 30¢,
       "5800.5"→580050, "19.99"×3, 1000×"0.01", "21474836.47" ok / ".48" 400,

     - spec/db/constraints_spec.rb: each DDL constraint rejects a raw

     - spec/requests/bulk_payments_concurrency_spec.rb (use_transactional_tests

  requests from the same payer run one after the other. The key is checked again
  after the lock, so the unique index cannot be hit in a race.
  - **Deadlocks:** All locks are taken in one statement with `ORDER BY id`
  ascending. Later foreign-key checks and `update_all` only touch rows the
  transaction already holds.

  exits the transaction block and rolls it back, which also clears `SET LOCAL`.
  - **Building the Arel `CASE` with `reduce`:** `when` and `then` change the
  node and return it, so the expression comes out right.
  - **Overflow in `Amount.parse`:** Inputs over 10 digits are capped at
  `OVER_MAX`, and the caller's range check rejects them.
  - **Ruby vs Postgres description checks:** Ruby's Unicode `[[:space:]]` is at

  before the insert, so a database check failure can't turn into a 500.
  - **Locals in `RequestParser#call` when the body is invalid:** The locals are
  nil there, and `fail_with_errors` raises before they are used.
  - **Payment IDs vs request order:** The sorted `nextval` IDs are zipped with
  the entries in request order, so payment IDs go up in request order as the
  comment says.
  - **`insert_all!` and the `readonly?` overrides:** `insert_all!` skips the
  model's `readonly?` and validations, and the records are never updated

  The bug

  curl -d '{…}' sends Content-Type: application/x-www-form-urlencoded by
  default. A JSON body containing % (for example a description of "100% 
  prepaid") got Rails' HTML 400. The same happened for an empty content type
  (406) and for a malformed query string like ?x=%. Rails parses the body and
  query string for request logging, before rescue_from applies. That broke FR-3
  (accept the body whatever the content type) and FR-7 (every error carries the
  error object).

  The fix is a process_action override in bulk_payments_controller.rb. It reads
  the body as JSON whatever the content type claims, and turns a BadRequest into
  the documented invalid_request 400.

  I checked it against a real server with curl:
  - A form-urlencoded request returned 201.
  - A replay of it returned 201 with Idempotent-Replayed: true.
  - A request with no content type returned 201.
  - A bad query string returned the JSON 400.
